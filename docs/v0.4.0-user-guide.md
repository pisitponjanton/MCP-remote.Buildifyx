# Buildifyx Desktop Agent v0.4.0 — Image & Browser Guide

**Status:** Prepared in the uncommitted working tree. Publishing, Cloud Production rollout, actual historic v0.3.2/v0.3.3 binary tests and Windows/Linux native Chromium validation are still **release gates**. This guide describes the Agent capabilities, not a promise that an older Cloud backend renders all image blocks.

## Install and upgrade

Requires Node.js 20.9.0+ and npm; use a supported recent LTS where possible. The package contains Playwright and Sharp dependencies. Browser automation also needs a **separate Chromium download**, which is not part of the npm tarball.

Install or upgrade the package explicitly:

`npm install -g @buildifyx/desktop-agent@0.4.0`

Check without accessing the network:

`bdxa --version`
`bdxa browser check`

Install a Playwright-managed Chromium browser **only when you want browser automation**:

`bdxa browser install`

This command invokes the CLI of the Playwright version installed alongside bdxa, for consistent browser/driver versions. You can alternatively run `npm run browser:install` inside the source checkout. There is no hidden browser install during `npm install`. If a restricted corporate network or offline host cannot download Chromium, browser tools remain unavailable but text, code and image-file tools are still usable. On Linux, the Chromium runtime may additionally need OS system libraries (consult Playwright's platform dependencies). `bdxa browser check` verifies executable presence only; an installed executable is not proof that required shared libraries are present or Chromium can launch. If Browser Tools return `BROWSER_LAUNCH_FAILED` explaining that Linux system libraries are missing, obtain administrator approval and install the **matching packaged Playwright Chromium OS dependencies** using that installed Playwright CLI's `install-deps chromium` command; then retry the Browser Tools. Installing Chromium again alone will not resolve missing `libgbm`, Cairo, Pango or other native dependencies. Do not automatically run system package installers or fetch browser binaries without explicit user authorization.

`bdxa browser check` checks the local executable and never downloads. Chromium is launched in a private headless user-data directory; bdxa never takes control of the user's normal Chrome/Edge profile. Chromium executable availability is affected by the current OS user and `PLAYWRIGHT_BROWSERS_PATH` environment setting.

## Cloud and Local MCP

**Cloud mode** (default): `bdxa login` once and then `bdxa -d --name backend`, or use `bdxa` for foreground mode. The Agent connects to Buildifyx Cloud, where the authenticated workspace must be online and selected or otherwise uniquely eligible. A Cloud backend must support negotiated Media v1 before image bytes are relayed; otherwise image tools return **local Artifact IDs/metadata only**, not image content in ChatGPT.

**Local MCP mode** (opt-in, no Cloud login): `bdxa local up`, then `bdxa local -d --name backend`, and use `http://127.0.0.1:3333/mcp` for local MCP clients. The Local gateway uses **No Auth** and must not be exposed publicly without access control; an HTTPS tunnel alone does not provide authentication. Local image content uses bounded per-instance IPC chunks.

Cloud Agent Protocol v2 and Management Protocol v1 are unchanged; newly added tools remain subject to the existing Agent permission checks. Browser and image features may not be available to old clients until a new tool scan or gateway/client reconnection.

## Image and artifact tools

- `read_image`, `get_image_info` and `resize_image` inspect/import/resize PNG, JPEG and WebP; decoded content is validated (up to 16 MiB, 8192 px per side and 16 million pixels; resize targets up to 4096 px).
- `get_cached_image`, `list_cached_assets` and `delete_cached_asset` inspect and manage temporary, owner-scoped cached assets. `clear_cache` deletes cache entries, **not** user-saved workspace files or Browser Persistent Profiles.
- `save_image` and `save_cached_image` are **explicit permanent saves** into the workspace or another separately permitted user-selected root. **R03:** `save_image` additionally requires independent `imageRead` permission for the source *and* `imageSave` for the destination. If either is Ask, that category requires approval; revoking either before writing stops the copy. They do not silently overwrite an existing path; path traversal and symlink checks apply.
- Local artifact cache: `~/.buildifyx/cache/v1/owners/<owner-key>/`. Default TTL is 24 hours and the quota is 1 GiB shared by the device. Cache is separated by device installation, canonical workspace, Local/Cloud namespace and **authenticated Cloud account**. New Cloud cache keys survive a token refresh when stable account ID is available. Old credentials use stored account email; credentials missing both rely on the device credential and may lose temporary cache access after token rotation. Legacy caches without account identity are not migrated automatically or reassigned to a different account, and explicitly saved workspace files are unaffected.
- Cloud/Local binary chunks are bounded to 128 KiB, with checksum/size checks and short-lived transfer authorization. **Binary delivery requires applicable imageRead/browserCapture policies to be Allow throughout the transfer.** Switching either permission to Ask/Deny cancels an existing transfer; switching back to Allow requires a new image request. A one-time Ask approval for a tool can allow metadata access but does not authorize continued binary streaming. Screenshot artifacts **and images derived by resizing screenshots** require `browserCapture` in addition to the image tool's permission, even when reading or saving through `get_cached_image`, `get_image_info`, `resize_image` or `save_cached_image`. At **Ask**, approval is requested for each protected operation; at **Deny**, protected bytes cannot be retrieved or sent. Screenshot entries are hidden from `list_cached_assets` unless `browserCapture` is **Allow**. Normal imported images continue to work independently. Legacy cached resizes marked `origin: generated` may also require `browserCapture`, even if they originally came from an ordinary image, because the old metadata did not preserve source lineage. New non-screenshot resizes use `origin: generated-safe` and are unaffected; legacy entries expire through the normal cache TTL. Explicitly saved workspace files are not erased on later revocation.

Example workflow: call `read_image({path:"design.png"})`, then `resize_image({artifactId,width:512})`. To keep a result, explicitly call `save_cached_image({artifactId,destinationPath:"output/design-small.png"})` after confirming the destination directory and permissions.

## ChatGPT image attachments and the Cloud import fallback (v0.4.0)

**Important:** A picture attached to or generated inside a ChatGPT conversation is **not automatically accessible** as raw bytes to the connected Buildifyx MCP tools. Current Buildifyx Cloud does not advertise a ChatGPT file-parameter input tool. Do not assume a model-visible preview can be copied to your machine. The direct attachment workflow has **not** passed a hosted ChatGPT E2E test.

Where your authenticated Buildifyx Cloud deployment exposes the image-upload tools, the explicit fallback is:

1. In ChatGPT, select the intended **online, MCP-enabled workspace** via Buildifyx. Call `create_image_upload` for that workspace and open its short-lived upload page.
2. **In a browser signed into the same Buildifyx account**, select a harmless PNG, JPEG or WebP (at most **4 MiB**) and submit it through the authenticated same-origin upload page. The ticket is one-time, owner/workspace/session-bound and expires after approximately five minutes. Image content shown in ChatGPT itself is not the uploaded file; you may need to download a generated/attached image first and then select that file on the upload page.
3. Call `get_image_upload_status` if needed, then `send_uploaded_image_to_agent({uploadId,targetId})` for the exact selected workspace. This requires Cloud support plus Agent v0.4.0 advertising `image-import-v1`, and local `imageRead=Allow` **and** `cacheManage=Allow`. No workspace image file is created at this step.
4. Use the returned temporary `artifactId` with `get_cached_image({artifactId})` to inspect verified metadata. The Agent keeps imported bytes **only in process RAM**, for up to **five minutes** (at most two imports per Agent). Disconnect, expiry, cache clear and permission revocation discard the temporary image; these imports are **not** the 24-hour disk cache described above.
5. **Separately and explicitly** call `save_cached_image({artifactId,destinationPath:'images/new-image.png'})` to create a new image file inside a previously approved destination folder. Local `imageSave` permission applies independently and Ask requires local approval; an existing path is never overwritten. The destination parent directory must already exist. Confirm the filename, metadata and checksum after saving.

`MEDIA_IMPORT_PERMISSION_REQUIRED` means local imageRead/cacheManage is not Allowed or the imported artifact is no longer authorized; `IMAGE_EXISTS` means choose a fresh destination; `CACHE_NOT_FOUND` means import again after expiry; `IMAGE_PATH_DENIED` means select an approved workspace location. A deployment with an older Cloud/Agent may return `UNSUPPORTED_CAPABILITY`; it cannot be fixed by bypassing local permissions or using Base64 through `run_command`/`write_file`.

**Release gate:** The described fallback interfaces and local tests exist, but a single authenticated **ChatGPT → hosted Cloud HTTP upload → installed Agent → explicit save** run has **not been verified**. Until a dedicated staging test completes, treat it as a documented integration path rather than guaranteed production behavior. The optional ChatGPT file-input method needs a separate Cloud feature and authorized real-client proof.

## Browser automation tools

1. `browser_open` starts an isolated **temporary** Chromium session and may open a URL.
2. `browser_navigate` navigates an authorized tab to HTTP(S).
3. `browser_snapshot` reads bounded visible text and element descriptions.
4. `browser_click` and `browser_fill` perform one verified action; targets accept a CSS selector, a role/name, or exact text.
5. `browser_tabs` manages up to five tabs; `browser_close` closes a session.
6. `browser_screenshot` takes PNG/JPEG images of the viewport, full page or one element into **temporary cache**. For responsive testing, use `viewportPreset:"mobile"` (390×844) or `viewportPreset:"desktop"` (1440×900), or custom `viewport:{width,height}`. `deviceScaleFactor:1..3` with `scale:"device"` returns native device pixels (e.g. mobile DPR 2 = 780×1688); `scale:"css"` retains CSS pixel dimensions. Device layout settings are temporary and restored after the screenshot; mobile emulation covers layout/DPR, **not** user agent or touch. Pass a prior screenshot's artifact ID via `compareToArtifactId` to report sampled before/after pixel differences. This does **not** automatically permanently save the image.
7. `browser_diagnostics` reports bounded, redacted console/page/network event types without exposing raw console messages, cookies, query strings, headers or response bodies.

A maximum of three Browser Sessions are active per tool owner by default, with a default idle lifetime of 30 minutes. Browser services use locally installed Chromium; they do not open an external browser UI.

Persistent logins require `browser_open({kind:"persistent",profileName:"approved-name",confirmPersistent:true})` **and** positive `persistentProfile` authorization. Cloud profile owners are tied to authenticated account identity rather than the rotating device token when account ID/email is available. After **explicit profile consent**, an old profile for the *currently signed-in device token* may be moved into the stable owner directory; unknown old-token profiles, running/locked profiles and existing destinations are left untouched. Profiles without any account data remain token-scoped. Those on-device profiles are under `~/.buildifyx/browser/v1/profiles/<owner-key>/`, with temporary sessions separately under `~/.buildifyx/browser/v1/sessions/<owner-key>/`. The profile snapshot may contain highly sensitive cookies. Password fields and form submissions require `confirmSensitive:true` plus separate approval; file uploads/downloads stay blocked. External websites require separate `browserExternal` approval; origin/popup/redirect restrictions apply.

The Browser Control permission categories `browserRead`, `browserNavigate`, `browserInteract`, `browserCapture`, `browserDiagnostics`, `persistentProfile`, `browserSensitive` and `browserExternal` default to **Ask**. Changing or revoking permissions can close sessions or abort transfers. Treat page content as untrusted; the implementation does not provide an OS-enforced network sandbox or guaranteed DNS pinning.

## Updating without losing an existing login

The installed npm package version and the **stored device login** are separate. Normal `npm install -g ...` or `bdxa update` changes program files and should not delete `~/.buildifyx/credentials.json`, instance settings, workspace plans or browser profiles. Do **not** run `bdxa logout` or `bdxa rm` merely to upgrade. After upgrading, verify `bdxa --version` and use `bdxa restart --all` to restart running background Cloud instances; if the Local gateway was active, `bdxa update --restart` can restart both Cloud and Local background instances.

The v0.3.2 / v0.3.3 **real signed-in binary upgrade matrix has not yet been verified**. Do not promise that no re-login is ever needed until Phase 11 executes that matrix. If login state is missing after an upgrade, diagnose the credential location and device identity first; do not automatically revoke or regenerate tokens.

## Packaging and validation

- `package.json` and `package-lock.json` declare v0.4.0; only the npm package is versioned, **not** the Agent v2 / Management v1 wire protocols.
- `npm run check`, `npm test`, `npm run pack:check` and `npm audit --omit=dev` are local gates. `pack:check` performs **npm pack --dry-run --ignore-scripts**; it does not publish or create a release tag. The npm tarball includes Agent sources, README, LICENSE and docs, but not browser executables, tests or credentials.
- macOS local Chromium and Cloud mock media integration were exercised in Phase 9. Windows/Linux, production Cloud, real signed-in v0.3.2/v0.3.3 binaries, npm-distributed tarball install on clean machines and ChatGPT MCP rendering are still Phase 11 release validation work. Final read-only `review_diff` is Phase 12.
