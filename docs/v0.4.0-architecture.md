# v0.4.0 — Agent Architecture and Ownership Decisions

Status: **Phase 1 design baseline, not an implemented feature**. This document maps the current v0.3.3 code and records decisions for Phases 2–11. No behavior or public protocol changes are introduced by this document.

## Goal and non-goals

Provide image read/edit/save, temporary local artifacts, browser automation and UI diagnostics in **both** Local MCP and Buildifyx Cloud MCP. Images and screenshots are temporary by default; durable files require an explicit save action. Keep browser login data on the user's device. Buildifyx Cloud acts as an authenticated relay, **not** permanent storage for image bytes, cookies, browser profiles or screenshots.

Out of scope: browser tools in Phase 1, live screenshot/image transport in Phase 1, silently reading ChatGPT chat attachments, taking over a user's normal Chrome profile, general-purpose screen recording, and unrelated refactors.

## Ownership model — decisions

### Identity

- `deviceInstallId`: opaque locally generated, stable identifier persisted with permissions restricted to the OS user. It is **not** a Cloud login token and never grants access by itself. Local and Cloud mode may share the same physical device identity but maintain separate authorization namespaces.
- `workspaceKey`: versioned SHA-256 key derived from a canonical real path and scoped to `deviceInstallId`/namespace. A path is canonicalized with platform-aware case handling. A rename/move yields a different key; no implicit permission transfer. Never rely only on `instanceId`, the workspace display name or Cloud target ID.
- `instanceId` / `targetId`: ephemeral routing and current-session selectors, retained for Agent Protocol v2 and existing Cloud quota/MCP gating.
- `sessionId`: independently random browser session identifier scoped to an authorized workspace/instance and requesting principal; not reusable after close.
- `artifactId` and `transferId`: CSPRNG-generated opaque identifiers, unguessable, not file names supplied by the client and not authorization credentials. Lookups always verify owner and current authorization.
- Cloud authorization additionally checks authenticated account/device, exact online instance, MCP Enabled workspace and permitted operation. Local mode checks the active local instance/workspace and its configured local policy. No cross-device or cross-workspace artifact access.

Even two live instances pointing to the same canonical path must not inherit one another's live browser sessions or pending transfers. Persistent workspace-scoped cache reuse is only permitted after reauthorization for the same stable owner.

### Storage

- Temporary image/artifact data: `~/.buildifyx/cache/v1/<owner-key>/...`, mode 0700 directories / 0600 files where supported. Metadata records schema version, owner, opaque ID, type, detected MIME, size, digest, creation/expiry, pin/lease state and origin; no user-selected path is concatenated into the cache path.
- Temporary browser sessions: `~/.buildifyx/browser/sessions/` with **separate** lifecycle/retention from image cache.
- User-opted-in persistent browser profiles: `~/.buildifyx/browser/profiles/`, private OS-user access, separate from temporary sessions and image cleanup. No auto-creation of persistent profiles and no sync to Cloud.
- Permanently saved images: ordinary files in the **authorized workspace root** or separately approved destination. Cache clear, browser close, workspace stop/remove and device disconnect never delete those saved files.
- Cache identity is stable across process restart and reconnect, but capabilities/permissions must be re-evaluated for every new process/request. Temporary artifacts do not grant indefinite access to a revoked device or disabled Workspace.

### Lifecycle, quotas and durability

- Proposed configurable defaults for Phase 2: **24-hour TTL** and **1 GiB total temporary artifact quota per device** (count bytes across namespaces; limit individual image pixels, compressed size and decode memory separately). These are proposed defaults, not current runtime behavior.
- Create via private temporary file + atomic rename, durable metadata, SHA-256 validation; reject symlinks/hardlink tricks and traversal, including path replacement between validation and final use (open/verify safely).
- Startup cleanup and periodic garbage collection remove only validated cache-owned entries. Evict oldest unpinned, unleased artifacts first; active readers/transfers hold leases. Fail closed if quota cannot be reclaimed. Prevent concurrent overwrite or deletion of in-use data.
- Expiration or crash recovery must not follow links or recursively delete arbitrary user paths; deletion audit excludes secret bytes. Clean partial transfers on cancellation/timeout.
- Proposed browser temporary session idle expiry is **30 minutes**, independent from image TTL; active sessions close on explicit close, shutdown or security revocation. Profile persistence requires opt-in and explicit reset/delete.
- Explicit save uses destination canonicalization, write permission plus separate outside-root approval, safe no-clobber default, atomic write and integrity check. A completed durable save remains after cache eviction. Avoid confusing a cache `pin` with an approved permanent save.

## Browser trust and permission policy

Use Playwright Chromium with isolated contexts; never silently attach to the person's regular Chrome/Chromium user profile. A web page, DOM, redirect, downloaded file, iframe, popup and network response are **untrusted**.

Proposed new policy categories in Phase 8: `imageRead`, `imageSave`, `cacheManage`, `browserRead`, `browserNavigate`, `browserInteract`, `browserCapture`, `browserSensitive`, `persistentProfile`. Until explicitly wired, unknown tools **must remain unavailable**. Default new sensitive operations to `ask` or `deny`, not inherited `allow` from v0.3.3's broad `read/write/command` defaults. Do not mutate existing user policies to implicitly grant categories.

Re-evaluate permissions on redirects, URL origin changes, new tabs, downloads and sensitive side effects (submissions, purchases, messages, destructive interactions). Support localhost for development **only with appropriate authorization**; block unsafe schemes and local-network surprises. Require explicit user approval before a persistent profile, uploading externally, storing durable images, or accessing outside allowed roots. Never log passwords, cookies, authorization headers, full page text or image bytes. Include cancellation, timeouts and concurrency limits on all browser operations.

Existing Local HTTP gateway has no authentication and may be tunneled by the user; keep its documented access risk visible. Future browser capabilities must not weaken local origin checks, workspace authorization or approval behavior.

## Mandatory regression checklist

1. Existing 11 v0.3.3 tools and their input schemas, default policy and manifest fingerprint are unchanged by Phase 1.
2. Agent Protocol v2 and Management Protocol v1 retain `device.ready`, `tool.call`, `tool.cancel`, `tool.result/error` and `management.*` semantics.
3. Cloud `deviceId + instanceId` routing, revoked-device close behavior, workspace MCP Enabled gating and plan quotas remain controlled by Cloud.
4. Local MCP remains loopback-only; Local instances still isolate settings under `~/.buildifyx/local`.
5. No image, cookie, profile or screenshot is durably stored on Cloud by default; if capability negotiation fails, return a deterministic unsupported-capability error, not silent downgrade to unsafe behavior.
6. Existing full-access mode **does not** bypass the newly required browser-profile consent, workspace identity fencing or external-action approvals.
7. Validate on macOS, Windows and Linux; document unavailable OS-specific smoke tests, and never claim unrun tests passed.
