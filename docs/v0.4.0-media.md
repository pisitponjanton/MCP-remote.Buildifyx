# v0.4.0 — Bounded Media Transport and MCP ImageContent

Local and Cloud media transfers use negotiated capabilities and bounded, verified chunks. A live deployment must be checked independently before claiming successful ChatGPT ImageContent delivery.

## Implemented components

- `src/transport/media/protocol.js`: version 1, 128 KiB raw chunks, max 16 MiB/image, four concurrent transfer sessions, 30-second idle timeout, SHA-256, sequential offsets, explicit finish/cancel, request/secret binding. Receiver bounds Base64 and fails closed on skipped/duplicate/corrupt chunks.
- `src/transport/media/local-agent.js`: tracks approved Image Tool requests for 30 seconds with a cryptographically random 256-bit secret and authorizes a single `media.open` per request; image bytes originate from workspace-scoped Cache after Phase 3 validation. No cache path is exposed.
- `src/local/gateway-server.js` and `src/cli/commands/local-instance.js`: Local MCP obtains validated chunks over repeated `media.open`, `media.chunk`, `media.finish` IPC commands instead of a single large JSON line. It emits actual MCP `{ type: "image", mimeType, data }` alongside readable metadata; `imageBytesDelivered: true` means this Agent's Local MCP response includes pixels.
- `src/transport/media/cloud-bridge.js` and `src/transport/cloud.js`: additive `capabilities.media` advertised in `device.ready` without changing Agent Protocol v2 or Management Protocol v1. Old Cloud receives the original JSON metadata. **Only** authenticated WebSocket responses explicitly accepting the media version, both features, exact instance and acceptable chunk size enable binary relay.
- `src/transport/media/upload.js`: an internal, opt-in upload assembler requiring caller-provided source/workspace authorization and validated temporary-Cache commit callbacks. Upload staging is **not** a public tool or connected to ChatGPT attachments/Cloud production.
- `src/transport/media/mcp-image.js`: validates MIME and SHA-256 again before constructing a supported MCP ImageContent block.

## Proposed Cloud wire messages — backend implementation required

An authenticated agent advertises `capabilities.media = {"version":1,"features":["transfer-chunks-v1","image-content"],"maxChunkBytes":131072}` on `device.ready`. A new Cloud Server may explicitly respond `media.capabilities.accept` with `{instanceId,version:1,features,maxChunkBytes}`. Without a valid accept, the Agent **must not send binary** and continues to return metadata with `imageBytesDelivered: false`.

For an Image Tool result, the negotiated Agent sends:

1. `media.transfer.open` with `{instanceId,requestId,transferId,artifactId,version:1,mimeType,size,sha256,chunkBytes}`; Cloud responds `media.transfer.accept` with the same `instanceId`, `requestId`, `transferId`, and `accepted:true`.
2. `media.transfer.chunk` with `{instanceId,requestId,transferId,index,offset,length,data}`, where `data` is Base64 for up to 131072 raw bytes. Cloud verifies each step and replies `media.transfer.ack` with matching identity/index and `offset` **after** the chunk was accepted. This per-chunk ACK provides backpressure.
3. `media.transfer.complete` with matching identities, `size`, `sha256`. Cloud verifies the whole asset and replies `media.transfer.received` with matching identities, `size`, `sha256`.
4. Agent sends legacy `tool.result` after the verified relay, with `mediaTransfer:{version,transferId,mimeType,size,sha256}` and `imageBytesDelivered:false` until the Cloud actually generates an MCP image block. Cloud must bind the staged bytes to the original authenticated account, online device/instance, enabled workspace, original tool call, result and MCP session; no cross-workspace reuse.
5. On error, cancellation, disconnect, revocation or timeout: terminate with `media.transfer.cancel`, release buffers and fail the request. A transfer never creates a permanent workspace file.

A Cloud implementation **must not** acknowledge accepted chunks before binding auth/scope and receiving the bytes. It must not persist passwords, cookies or raw screenshots in permanent Cloud storage. Use TLS/WSS. The 128-KiB raw chunk keeps each JSON Base64 frame well below the Agent's existing 4 MiB WebSocket input limit.

**Compatibility boundary:** This wire schema is a defined Agent proposal awaiting exact Cloud-side implementation/review. An old Cloud may ignore media capability fields. No production support should be claimed until the Cloud service implements the same messages, enforces MCP Enabled and ownership **on every chunk**, and serializes a real MCP ImageContent block in its MCP response.

## Limits and security considerations

- Successful Local transfer includes image pixels; text-only clients also receive metadata, and may ignore an image block if their MCP implementation does not support it.
- **Phase 13 R01:** Local and Cloud outbound binary ImageContent are allowed only while the current `imageRead` or `browserCapture` category (plus browserCapture for screenshot-derived artifacts) is **Allow**. A transition from **Allow to Ask** is a revocation for that existing transfer, not merely a pause. Local cancels the authenticated transfer and clears staged data; Cloud sends a cancellation frame instead of completion. Returning the policy to Allow requires a fresh Tool Call/transfer. A one-time Ask approval may permit tool metadata but does **not** automatically allow ongoing binary delivery. Verified in `test/media/provenance-revocation.test.js`.
- Actual read/resize/cache tools still require `imageRead` approval; no permission is bypassed by the transport. Local IPC uses the authenticated instance control endpoint plus a gateway-generated 256-bit per-request secret. A transfer handle is not a user-facing authorization token.
- Base64 is used only in bounded individual local IPC or Cloud WS chunk envelopes; no multi-MiB raw image is inserted into legacy `tool.result`. A final MCP image content block necessarily includes the bounded Base64 image, subject to client size limits.
- Input image limits and MIME decoding are enforced by the Phase 3 Image Service before images are cached or fetched. Direct upload staging must invoke the same validation in its `commitImage` callback; until an authenticated upload source is implemented, the upload registry must remain internal and unexposed.
- No implicit access to images attached in ChatGPT messages. Import requires future Cloud-authorized staging/upload plumbing and practical client tests.
- The Cloud Agent validates the WebSocket peer's capability acknowledgement and checks request/instance on each ACK. It cannot independently prove that the Cloud Server has reauthorized a workspace after disabling MCP; that enforcement must occur server-side. Unexpected or missing acknowledgements fail closed.

## Cloud v0.4.0 Phase 11 addition — opt-in inbound image import (unreleased)

Historical sections above describe the original Agent→Cloud relay. The uncommitted Agent now also advertises the optional `image-import-v1` feature, requiring the Cloud to explicitly include it in `media.capabilities.accept` before inbound import is handled. `media.import.open/chunk/complete/cancel` and `media.import.accept/ack/received/error` use the existing authenticated WebSocket. The Cloud sends at most 128 KiB per ACKed frame, a SHA-256-verified image of at most 4 MiB; Agent also validates canonical Base64, MIME magic, full-image decoder correctness, order, Agent instance and current socket.

The user must first open the same-account explicit Buildifyx upload page. MCP `send_uploaded_image_to_agent` consumes a one-time upload only after verifying the selected Agent advertises import. The Agent requires local **imageRead=allow and cacheManage=allow** (ask/deny never auto-approved), stores imported images exclusively in process RAM for five minutes, clears on disconnect/revocation/cache clear, and isolates from the disk artifact cache. A permanent workspace file is possible **only** through a distinct explicitly authorized `save_cached_image`. No ChatGPT attached/generated image is accessed without the user's provided upload bytes. Old Agent/Cloud combos keep legacy MCP behavior.

Cloud mock ACK/revocation/invalid reply and actual Agent WebSocket/RAM-store tests pass, but real ChatGPT/production/auth upgrade, multiworker upload affinity, and the Agent's other open browser/cache security findings still block release. No claim of deployed support.
