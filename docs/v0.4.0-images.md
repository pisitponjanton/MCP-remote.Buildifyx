# v0.4.0 Phase 3 — Image and Permanent-save Tools

Status: **Phase 3 implementation baseline, not published**. Uses sharp 0.35.5 for PNG/JPEG/WebP decoding and resizing. The Phase 4 transport work now supports real ImageContent for Local MCP; Cloud relay still requires explicit backend capability acknowledgement and Cloud-side implementation. See [Phase 4 transport details](./v0.4.0-media.md). ChatGPT attachment import remains unsupported.

## MCP tool contracts

| Tool | Inputs | Result and side effect |
| --- | --- | --- |
| `read_image` | `{path}` | Validates/decodes workspace image, caches it temporarily, returns metadata, `artifactId` and `imageBytesDelivered: false` |
| `get_image_info` | `{path}` **or** `{artifactId}` | MIME, dimensions, size and SHA-256 only |
| `resize_image` | `{path}` or `{artifactId}`, `width?`, `height?`, `format?` | Creates a bounded temporary resized image; returns `artifactId` and metadata only |
| `save_image` | `{path, destinationPath}` | Explicitly creates a permanent copy from a workspace file; never overwrites |
| `list_cached_assets` | `{}` | Lists image/screenshot metadata owned by current workspace |
| `get_cached_image` | `{artifactId}` | Returns validated metadata with `imageBytesDelivered: false` |
| `save_cached_image` | `{artifactId, destinationPath}` | Explicitly creates a permanent file under approved destination; holds cache lease during save |
| `delete_cached_asset` | `{artifactId}` | Removes this workspace's temporary cache entry |
| `clear_cache` | `{}` | Removes this workspace's temporary cache entries only; does not delete saved files |

No tool accepts a base64 image or attachment bytes from ChatGPT in this phase.

## Permissions

- `imageRead`: image and cached-image reading/inspection/resizing
- `imageSave`: explicit permanent save
- **R03 (Phase 13):** `save_image` reads an existing workspace image before creating the permanent copy, so it requires **both** `imageRead` (source) and `imageSave` (destination). They are evaluated and approved separately, including Ask decisions. Downgrading either permission while the request is pending or before the exclusive destination create fails closed. Source and destination `outsideRoot` approvals remain independent. `save_cached_image` retains its existing separate cached-artifact permissions.
- `cacheManage`: temporary cache listing/deletion/clear
- All three **default to Ask** (even if the v0.3.x `read`, `write`, or unrestricted-command settings are Allow). Cloud/Local tool dispatch goes through the existing approval controller.
- Source `path` and `destinationPath` are classified independently. An outside-root source or destination requires a separate `outsideRoot` approval. Approving the destination does not approve the source or grant imageSave.
- Permanent save creates only new files with exclusive/no-follow flags and restrictive permissions. Existing files and user project files are never overwritten or deleted by cache operations.
- The artifact ID is not a capability token: cache always enforces a stable device/workspace/namespace owner key.

## Validation and resource limits

- Magic bytes must be PNG, JPEG or WebP; declared content type of an existing cache artifact must match detected bytes.
- Malformed files and images beyond **16 MiB** input, **16 million pixels**, or **8192 px per source dimension** are rejected. Resize dimensions must be 1–4096 px; the `inside` fit never enlarges.
- Sharp decoder errors are normalized without exposing decoded image content or environment data. Output encoding strips metadata by default and is checked again before caching.
- Cached images inherit Phase 2's 24-hour TTL, one-GiB per-device cache quota, integrity checksum, filesystem lock and temporary lease model.
- A permanent destination is reclassified before creating the file. Creation fails if a file already exists, including a symlink. Access to `.git` internals and Buildifyx private state remains forbidden.
- OS-level tests run on the connected macOS host; Windows/Linux native-image and filesystem smoke tests remain required in the final release validation phase. A malicious concurrently replaced **parent directory** is a remaining platform-specific race to assess during final security review; Node's portable filesystem API does not provide an atomic openat-style parent anchoring guarantee.

## Integration boundaries

- Tool schemas are added to the MCP registry used in Cloud and Local routing. Image services join the existing runtime dispatcher; there is no new public port or second MCP server.
- In Local mode the runtime uses the `local` cache namespace. Cloud uses `cloud` and continues enforcing account/device/workspace online/MCP Enabled at its existing gateway.
- `imageBytesDelivered: false` is intentional until Phase 4 implements authenticated bounded binary transport, MCP ImageContent, and confirmed client compatibility. Clients may inspect dimensions and use a cached artifact ID but cannot receive image pixels through current MCP.
- Existing Agent Protocol v2 and Management Protocol v1 are unchanged. Package version remains 0.3.3 until planned v0.4.0 packaging phase.
- Phase 8 will broaden consent UI, redaction, sensitive-browser permissions and OS-specific hardening. Phase 3 only introduces the narrow image permission categories and independent path checks.
