## Security finding and minimal fix

**HIGH — transient import could be saved after source permission/cache revocation during asynchronous destination validation.**

Prior code in `src/image/service.js` checked local `imageRead=allow` and `cacheManage=allow` before `writeDurable`, but not again at the last authorized destination-write checkpoint. With a policy downgrade/temporary-RAM clear during the asynchronous path-classification step, the `temporary.data` Buffer was zeroized, yet `imageSave` could still pass and a file containing zeros could be created.

A deterministic regression reproduced the bug before the fix: `test/media/phase4-image-security.test.js` **12 pass / 1 fail**, with `Missing expected rejection` in `revocation at late permanent-save checkpoint`.

**Fix:**
- For imported RAM images only, `save_cached_image` creates a private snapshot of the incoming Buffer for the authorized save, and zeroes this snapshot in `finally`.
- Revalidates import permissions plus original artifact identity/TTL immediately after Sharp decode and after asynchronous destination-path validation, at the last `assertStillAllowed` checkpoint. This supplements, and never weakens, the existing `imageSave` permission and destination-root evaluation.
- Revocation/TTL/cancel **before** the commit boundary prevents file creation. RAM revocation/clear **after** an already authorized commit cannot corrupt in-flight output bytes. Source/import RAM still zeroes at disconnect or revocation.
- No change to MCP tool names/schema, Agent/Management protocol, Cloud endpoints, import size cap, non-import cached-image behavior or permission defaults.
