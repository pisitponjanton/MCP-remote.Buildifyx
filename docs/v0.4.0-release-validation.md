## Historical npm binaries and credential-preserving upgrade

Actual npm registry artifacts **0.3.2** and **0.3.3** were fetched and independently installed using `npm install --prefix /tmp/... --ignore-scripts`, with *no* global npm changes. Each old CLI ran with a disposable `HOME`, `BUILDFYX_HOME` and signed-in **synthetic device credential** accepted by an authenticated loopback HTTP/WebSocket Cloud mock.

| Historical flow | Old binary → simulated Cloud | npm install to 0.4.0 in SAME prefix | Credential bytes unchanged | New binary → simulated Cloud |
| --- | --- | --- | --- | --- |
| v0.3.2 → v0.4.0 | PASS, device.ready Protocol v2 + real `read_file` tool result | PASS | PASS, byte-for-byte | PASS, device.ready Protocol v2 + real `read_file` |
| v0.3.3 → v0.4.0 | PASS, device.ready Protocol v2 + real `read_file` tool result | PASS | PASS, byte-for-byte | PASS, device.ready Protocol v2 + real `read_file` |

The old and new binaries executed **against the same simulated Cloud** separately. This is much stronger than changing a version string in a unit test. It demonstrates preservation of stored credential data, device ID, WebSocket handshake and a legacy MCP tool under the fixture.

**Boundary:** These were disposable *synthetic* credentials, not an actual customer's signed-in session. The mock was not the production `bdxa.buildifyx.com` backend or the deployed v0.4.0 Cloud implementation. Real backend login/refresh behavior and live device upgrades are **not confirmed**. Running `npm install --ignore-scripts` for reproducible validation also does not test third-party install lifecycle scripts.

Reproduce network-capable historical-version validation with `node scripts/release-validate-installed.js /tmp/<isolated-package-prefix>` after staging the historical npm artifacts and local v0.4.0 tarball. The script uses ephemeral per-run home/credentials and upgrades each prefix in place.

## Actual fresh v0.4.0 tarball smoke

Installed the generated local tarball with its npm dependencies into an isolated test prefix, then loaded the *installed package files*, not Source Checkout modules:

- PASS: version metadata 0.4.0, **29 MCP tools**, and separate Ask defaults for image/browser/sensitive/external/persistent permissions.
- PASS: read a real PNG, resize with installed Sharp, place the result in owner-scoped temporary cache, explicitly save it to workspace, reject overwrite, and clear cache while retaining the saved file.
- PASS: installed-package CLI `--version` returned 0.4.0; `browser check` correctly returned an unavailable indication and nonzero status for the matching Chromium binary.
- Installed fresh dependencies resolved **Playwright 1.64.0**, **Sharp 0.35.5**. The Source Checkout's npm lock/test environment used **Playwright 1.56.1**. The package's `^1.56.1` semver range allows this divergence.

**Release gate:** Browser binaries for the newly resolved Playwright 1.64.0 were NOT downloaded or launched in this smoke test. Browser/Chromium tests passing from the checkout with Playwright 1.56.1 **do not prove** a fresh npm install with Playwright 1.64.0 is browser-operational. Before release, align and test the exact installed Playwright/Chromium pairing on clean environments (and consider dependency version pinning/lock strategy). Do not silently install Chromium on users' devices. Run the opt-in `bdxa browser install` only with user consent; verify without side effects via `bdxa browser check`.

Reproduce isolated artifact smoke with `node scripts/release-validate-tarball.js /tmp/<prefix-with-installed-v0.4.0>`.

## Verified Agent integration and outstanding qualification

Already validated in Phase 9 and repeated in source regressions on this host: real macOS Chromium Browser/Open/Click/Snapshot/Save, Local MCP tool relay and IPC image chunks, Cloud Agent Protocol v2 Mock with media capability negotiation/ACK/checksum and no-media fallback, authenticated instance routing, session teardown on disconnect, cancellation, screenshot permission revocation, and persistent-profile cookie restore.

**Still unverified / release blockers:**
1. **Cloud Production** and real ChatGPT MCP image rendering, including deployed Server Media v1 negotiation and backward compatibility with *deployed* v0.3.x Cloud semantics.
2. **Native Windows and Linux** (Node v20.9+/supported runtime, Chromium dependencies, Playwright browser installation, Sharp platform native packages, Local socket/IPC, persistent profile management).
3. **Fresh-install Playwright/Chromium compatibility** for the semver-resolved version, and test on the declared lowest supported Node version (tests ran under Node 24).
4. **Real signed-in device upgrade** / token refresh/session validity with the deployed Cloud backend. The synthetic-token upgrade preserved credentials, but is not an end-to-end production-auth qualification.
5. **Network policy/security caveat:** Browser's Playwright request interception is not a guaranteed OS-enforced firewall/DNS pinning or complete DNS-rebinding defense.
6. Final **Phase 12 read-only diff review** of all uncommitted changes, with blocking findings addressed before any publication.

## Decision and cleanup

**Phase 11 validation work is complete, but the v0.4.0 release remains ON HOLD** pending gates above and a successful Phase 12 diff review. Nothing was committed, pushed, published or deployed. Repository version was already bumped to 0.4.0 in Phase 10; no npm registry version was published by validation. This report is an evidence record, not a release authorization.
