# v0.4.0 — Permissions, Approvals and Privacy

Browser, image and filesystem actions remain controlled by the local Agent's authorization policies. Sensitive actions require explicit permission, and local protection mechanisms have documented limitations.

## Permission model

| Category | Default | Enforces |
| --- | --- | --- |
| `browserRead` / `browserNavigate` / `browserInteract` | Ask | Browser session access, navigation, safe interactions |
| `browserCapture` / `browserDiagnostics` | Ask | Screenshot pixels and redacted diagnostics |
| `persistentProfile` | Ask | Opening a user-approved persistent local browser profile |
| `browserSensitive` | Ask | A particular click/form submission or password input **with** `confirmSensitive:true` |
| `browserExternal` | Ask | Explicit `browser_open` or `browser_navigate` to a non-loopback HTTP(S) origin |
| `imageRead` / `imageSave` / `cacheManage` / `outsideRoot` | Ask | Image/cached data, permanent save, temporary cleanup, non-workspace filesystem paths |

The first-pass permission evaluation runs through existing Local/Cloud Agent permission gates. Browser login profiles are not created unless both `confirmPersistent:true` and separate `persistentProfile` approval are present; missing confirmation is rejected before prompting. For sensitive clicking or filling, the tool must explicitly pass `confirmSensitive:true` and `browserSensitive` must be approved. Without both, form/submit/password-sensitive actions are rejected. File uploads and download-link clicks remain blocked regardless of the Sensitive approval. Full command access does not bypass browser categories.

All Browser results remain bound to the trusted Agent instance, principal, device, namespace and canonical workspace (not client-provided identity fields). At time of action execution the Agent checks the latest policy, and previously granted rights cannot override a subsequent `deny` or downgrade from `allow` to `ask` during the same request. Revoking `browserRead`, `browserNavigate` or `browserExternal` closes active Browser Sessions; revoking `persistentProfile` closes affected persistent sessions. Existing approved local profile files remain on-device and are not erased by image-cache cleanup or revocation.

## Origin and network baseline

**Phase 13 R02:** Each Browser tab now has its **own explicitly authorized origin**; `browser_open` or `browser_navigate` validates the URL and replaces only that tab's origin. The Browser Context still intercepts all requests, but a request must belong to the very tab that authorized its origin. Another tab's navigation, Sensitive Approval or site permissions never authorize the request. Requests without a trustworthy originating frame (including popup/service-worker network requests) fail closed. Navigation to a new origin removes the previous origin for that tab. Chrome tab closure releases its grant. The redirect response and follow-up checks apply to the same originating tab, not a context-wide allowlist. Tested with real Chromium on three independent localhost origins in `test/browser/r02-origin-isolation.test.js`. Each intercepted request is evaluated by scheme, origin, method and public-address safety checks. Playwright fetches with redirects disabled, checks 30x Location against approved origins and fulfills only authorized responses, rather than relying on `route.continue` to inspect redirects. Background non-GET/HEAD requests and script-driven fetch/XHR requests (including GET) are denied by default. After an unapproved-safe `browser_click` or `browser_fill`, the **affected tab** blocks all new HTTP requests, including delayed GET fetch, image beacons, and anchor/JavaScript navigation, until an explicit `browser_navigate` on **that same tab**. Navigating a separate tab must not unlock its requests. Explicit Sensitive Action approval is also scoped to its originating tab, not the whole browser context. This intentionally means some SPAs and even ordinary links will need explicit navigation or a separately approved sensitive action. A `confirmSensitive:true` click/fill with actual `browserSensitive` approval can temporarily permit same-origin network requests during that one action; it does not grant permanent approval or authorize an unrelated origin. Popup windows opened by sites are closed, and websocket connections are blocked by Browser Context interception. `localhost` and explicit loopback URLs remain available for local development.

**Security limitation:** HTTP method, button label and page HTML cannot prove whether a remote server interprets a GET as read-only. Even explicit `browser_navigate` to an approved URL can have server-side consequences. The read-only interaction guard is a fail-closed Agent control, not a guarantee that visiting untrusted sites is side-effect free. The DNS validation and Playwright-level interception do not guarantee system-level DNS pinning or stop every possible DNS-rebinding/Chromium networking edge case. On untrusted networks, additional OS-level egress isolation/proxy pinning and cross-platform verification are still recommended before promising unrestricted production browsing. Existing authorised sites may observe same-origin requests and can contain sensitive information. This is an Agent-side permission defense, not a full sandbox.

## Privacy, cancellation, and storage

- `browser_fill` values, Browser CSS/text targets and full input URLs are redacted from the Tool and Approval audit events. Browser response URLs are reduced to origins; common credential-like strings in snapshot text are masked. The user-requested page content may still be sensitive, so `browserRead`/`browserCapture` approvals remain separate.
- Sensitive password fills never echo password values or even their length. Raw console messages, stacks, cookies, query strings, headers, response bodies and screenshots are not included in Browser Diagnostics.
- Existing approval cancellation rejects pending actions before execution; the tests cover cancelling a Sensitive request before approval and verify no form submission. Sensitive clicks and permanent saves may become irrevocable once side effects begin; this is **not** a rollback guarantee for requests already committed.
- **Phase 13 F02 hardening:** screenshot metadata/bytes, `get_cached_image`, `get_image_info`, `resize_image` and `save_cached_image` require **both** the image tool's normal permission and `browserCapture` when the cached artifact was captured by the browser. If `browserCapture` is **Ask**, the request receives a separate approval; if **Deny**, it fails. Image resizes derived from screenshots retain `origin: capture` so they cannot be reclassified as ordinary images to bypass this control. Legacy cached `origin: generated` entries are conservatively treated as capture-protected because older Image Tools did not record source lineage. Newly generated normal-image resizes use `origin: generated-safe`. Old generated entries remain subject to the normal temporary-cache TTL; this is a deliberate short-lived compatibility restriction. `list_cached_assets` omits protected screenshot/derived entries unless the active `browserCapture` policy is **Allow**; deletion/clearing of those entries remains permitted with `cacheManage`.
- Local media transfer and Cloud media negotiation recheck the **actual artifact provenance** at open and each chunk, not merely the MCP tool name. **Phase 13 R01:** binary transfer requires the relevant categories to remain explicitly **Allow**; downgrading imageRead or browserCapture to **Ask** or **Deny** stops the transfer even when the original Tool Call had an earlier approval. The Local agent invalidates the transfer and releases its bytes so re-enabling Allow cannot resurrect old transfer handles. Cloud sends media.transfer.cancel and never completes the downgraded transfer. This closes `get_cached_image` binary-transfer bypasses after `browserCapture` is set to **Deny**, even if `imageRead` remains **Allow**. Capture data already saved as an explicitly user-approved permanent workspace file is a normal workspace file and is not retroactively deleted.
- **Phase 13 F03 hardening:** Cloud Cache ownership is derived from authenticated Cloud origin plus stable account ID (or older stored account email), together with installation ID, namespace and canonical workspace. If account identity is missing, a device-credential hash avoids cross-account reuse but is sensitive to token rotation. Legacy unscoped caches are not migrated to a new account or deleted during migration. Cache injection cannot silently change its bound principal. Authenticated users cannot list/read/save/clear another account's cache; global-quota eviction is limited to the current bound owner. See `test/cache/f03-isolation.test.js`.
- **Phase 13 F04 hardening:** Browser persistent profile storage uses authenticated account-stable ownership separately from token-specific live-session access. Migration is performed only after explicit Persistent Profile approval, only for a validated named old profile tied to the currently known device token, and only while holding old/new profile locks. Unsafe links, a live/stale old lock, or a pre-existing destination block migration without deleting files. Old-token identities are not enumerated or inferred; profiles with no stored account identity remain token-dependent. Verified with `test/browser/f04-identity.test.js`, including real Chromium cookie recovery after device-token rotation.
- **Phase 13 F05 screenshot display emulation:** mobile/desktop presets and custom viewport/deviceScaleFactor are bounded and temporary. Browser `browserCapture` approval is still required; snapshots are verified by the same private Image Cache and byte/pixel limits. Chromium CDP metrics apply to the selected tab only and are removed after capture; the original Page viewport is restored. The mobile layout preset does **not** impersonate a real device user-agent or enable touch. Verified with `test/browser/f05-device.test.js`.
- **Phase 13 R03 source authorization:** `save_image` requires independently approved `imageRead` (existing source) and `imageSave` (new destination), in addition to applicable outside-root approvals. Both permissions are rechecked before reading bytes, after decode and immediately before exclusive destination creation. Revoking either from Allow to Ask/Deny during the request rejects the copy without creating a destination. Verified by `test/image/r03-source-permission.test.js`.
- Browser temporary data, temporary image Cache, and user-approved persistent local profiles remain different owner-scoped storage lifecycles. Permanent image output continues to use explicit `save_cached_image`/`save_image` with path/symlink/overwrite protections. Neither revoking a browser permission nor clearing the cache deletes user-approved files or profile data.

- `test/browser/f01-network.test.js`: real Chromium denial of hidden/delayed GET and POST, image-beacon and link requests after safe interactions, non-sensitive fill, per-action approved GET, and cross-tab lock/approval isolation.

- Existing Browser/Chrome, image/cache, Local MCP, Cloud Mock and media chunk tests remain active and are rerun in full.
- Phase 9 is reserved for expanded Agent Local/Cloud integrations, identity/permission matrices, and compatibility checks. Version bump, platform browser smoke, old Agent version matrix, real Cloud integration and release validation are later phases.

Do not claim the browser can safely perform purchases, arbitrary uploads, personal Chrome takeover or unrestricted intranet access on the strength of these tests. No commit, push, npm publish or deployment is included in Phase 8.
