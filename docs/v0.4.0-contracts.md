# v0.4.0 — Draft Capability and Binary Transfer Contract

Status: **Phase 1 design baseline**. Phase 4 now implements a versioned Agent-side media transport with mock Cloud acknowledgement, documented in [Phase 4 Media Transport](./v0.4.0-media.md). The production Cloud implementation and ChatGPT ImageContent interoperability are **not yet confirmed**, so older peers continue using Agent Protocol v2/Management Protocol v1 with JSON metadata and no binary upload. This document retains original proposed mechanisms for comparison; refer to the Phase 4 document for implemented message names.

## Current invariants

- Agent Protocol `2` and Management Protocol `1` remain unchanged. `device.ready` includes manifest `count`, `hash`, `manifestVersion` and optional tool names; current management `capabilities` advertises its own version/actions.
- Cloud `tool.call` uses `requestId`, `instanceId`, `tool` and JSON `arguments`; success is `tool.result` with JSON `result`. `tool.cancel` requests cancellation. Cloud inbound `maxPayload` = 4 MiB.
- Local `/mcp` gateway invokes per-instance control over a line-delimited JSON socket and currently receives one JSON object per request. There is no safe large-binary transport yet.
- Existing `successResult` returns JSON as text and structuredContent, not binary MCP ImageContent. Do not represent an artifact ID alone as proof the MCP client received image pixels.

## Opt-in feature negotiation (proposal)

Advertise additive `capabilities.media` on `device.ready`, keeping the existing fields intact:

`{"capabilities":{"managementVersion":1,"actions":["..."],"media":{"version":1,"features":["image-content","transfer-chunks-v1","browser-tools-v1"],"maxChunkBytes":262144}}}`

Cloud must explicitly acknowledge supported media version/features after authentication and workspace access checks. **Only the intersection is enabled**. The exact ack message name is to be agreed with the Cloud project in Phase 1/4; until this agreement, treat media as unsupported. Older servers ignore the extra field and continue to work. Feature flags and tool manifests represent what the running Agent actually implements, not what the roadmap promises.

- If Cloud lacks transfer-chunks-v1, fail image requests needing bytes with an explicit `UNSUPPORTED_CAPABILITY` result. Do not stuff giant base64 into `tool.result` as a fallback.
- Text/metadata fallback is allowed only when explicitly useful and accurately labeled `image bytes not delivered`. ChatGPT attachment contents are **not** implicitly available to an MCP tool. Import from a chat requires tested byte forwarding, or explicit user upload to an authenticated, workspace-scoped staging endpoint.
- Restrict Cloud MCP visibility by device/account, online workspace and `MCP Enabled` **before** tool dispatch or transfer opening. Enforce again on each chunk and save.
- Never return a transfer handle that another device/workspace/account can reuse. Explicitly check capability/version, requested MIME and resource limits.

## Media operation outline

Planned Agent tools (names become real only when registered, not in this phase):

| Tool family | Planned names | Result |
| --- | --- | --- |
| Image | `read_image`, `get_image_info`, `resize_image`, `save_image` | Validated PNG/JPEG/WebP image or metadata; saves require explicit destination/approval |
| Cache | `list_cached_assets`, `get_cached_image`, `save_cached_image`, `delete_cached_asset`, `clear_cache` | Owner-scoped metadata/bytes/delete result |
| Browser | `browser_open`, `browser_navigate`, `browser_snapshot`, `browser_click`, `browser_fill`, `browser_tabs`, `browser_close` | Isolated session handles and bounded DOM/action results |
| Inspection | `browser_screenshot`, `browser_diagnostics` | Owner-scoped screenshot artifact and bounded diagnostics |

MCP image result on supported clients should contain a real `{type:"image",data:"...",mimeType:"image/png"}` content block **at the MCP boundary** after bounded transfer; it must be tested end-to-end. For large images, downscale/limit or explicitly report a size error; do not inline arbitrarily large image payloads. Preserve structured, sanitized metadata for clients that do not support image blocks.

## Transfer envelope (proposal, version 1)

`transferId` and `artifactId` are opaque random IDs. Transfer state is keyed by authenticated principal, deviceInstallId, workspaceKey, current instance/session and request ID; metadata is not an authority token.

1. **Offer/open**: declare `transferId`, `artifactId` (when reading existing asset), direction (`upload`/`download`), authorized purpose, `mimeType`, byte length, SHA-256, max chunks, expiry and expected destination ownership. Upload is denied unless the user selected an explicit approved source or staged upload.
2. **Accept**: peer validates negotiated capability, authenticated owner, size/mime/usage quota and workspace MCP Enabled status. Receiver returns bounded chunk window and an optional resume offset only for a still-valid same-owner session.
3. **Chunk**: monotonically numbered `index` and bounded `offset`, `length`, payload; proposed raw chunk maximum **256 KiB**. Cloud framing may use authenticated binary frames or base64 within **small** control envelopes by explicit agreement; **never** a giant JSON base64 image. Validate per-chunk boundaries and overall caps; reject duplicates, gaps and excessive in-flight chunks.
4. **Ack/backpressure**: receiver acknowledges a verified offset, and sender pauses at the negotiated window. Cancellation and network failure release leases and staging handles.
5. **Complete**: compare total byte count and SHA-256, magic-byte sniff MIME, decode/pixel limits for images, atomically commit to the temporary cache and return owner-scoped `artifactId`. Never implicitly create permanent files.
6. **Cancel/expire**: explicit cancel, request cancellation, disconnect, owner revocation, quota pressure and timeout close the session and safely delete only transfer staging data. A revoked session cannot resume.

Suggested control event names for joint review: `transfer.open`, `transfer.accept`, `transfer.chunk`, `transfer.ack`, `transfer.complete`, `transfer.cancel` and `transfer.error`. **They are placeholders** until Cloud and Agent agree on wire message shapes, duplicate/retry semantics, direction handling and MCP ImageContent support. An implementation must not silently assume they are supported today.

### Local transport

Use an explicitly chunked instance-control path (multiple bounded `artifact.read_chunk` / `artifact.write_chunk` messages or a separate authenticated local binary channel) instead of the existing single line-delimited JSON `tool.call` response for pixels. Require session/instance/workspace ownership and bind chunk tokens to the invoking MCP request. The local gateway must assemble/stream only within configured image limits, cancel if client disconnects and emit MCP image content (or a clear unsupported result). It must not expose private cache paths over HTTP.

### Cloud transport

Only transfer through the authenticated WSS relay or an equivalently authenticated, explicitly approved temporary upload endpoint. Keep individual WS frames safely below 4 MiB (including encoding overhead), and bound queued bytes, concurrent transfers, CPU/memory and idle timers. The Cloud is a transit path: delete staging bytes after completion/timeout, do not write image files/browser profiles/cookies to permanent storage, and redact credentials from logs. A reconnect requires reauthorization; never replay an action or deliver a chunk across a changed owner/instance.

## Compatibility and error matrix

| Peer/client scenario | Required behavior |
| --- | --- |
| New Agent + old Cloud | Legacy tools work; new image/binary operations fail explicitly with `UNSUPPORTED_CAPABILITY` if transfer unavailable. |
| Old Agent + new Cloud | New tools not listed, or Cloud rejects with known unsupported-tool result; existing tools still work. |
| Local MCP client supports images | Deliver valid MCP ImageContent with bounded bytes and correct detected MIME. |
| MCP client is text-only | Honest metadata/fallback; never claim that image bytes were delivered. |
| Cloud workspace offline or MCP disabled | Reject opening, continuation and direct-target access; cancel ongoing transfer on revocation. |
| Transfer interrupted/corrupted | Reject mismatched SHA-256/length/order, clean staging, no partial save. |
| Multiple instances same workspace | Cache access only after authorization by stable owner; sessions/transfers remain instance-scoped. |
| User explicitly saves an image | Create file in approved path; cache deletion or instance removal does not remove it. |
| No ChatGPT attachment-byte path | State unsupported import and offer explicit authenticated user-staging path once implemented. |

## Phase 4 verification required before enabling features

- Cloud and Agent agree a versioned **exact** wire schema and acknowledgement (including older-version behavior); tests simulate Cloud v0.3.x and v0.4.x.
- An end-to-end test sends a multi-MiB image using chunks smaller than the 4 MiB incoming WS limit and verifies SHA-256, ordering, cancellation, quota and transfer ownership.
- Local IPC path transfers an image through the MCP gateway without a single huge JSON response.
- MCP `ImageContent` is actually received and rendered/interpreted by a supported client; ChatGPT behavior is tested separately instead of assumed.
- Authorization tests reject cross-device/workspace, disabled MCP access, symlink escapes and attempted permanent save without approval.
- Metadata/log traces do not reveal image bytes, profile cookies, tokens or credentials.
