# v0.4.0 — Isolated Browser Engine

Technical notes for local Chromium session lifecycle, context isolation and approved browsing. Browser automation does not imply access to a user's personal browser profile.

## Implementation

| Component | Responsibility |

## Filesystem identity and storage

All data stays on the **user's computer**. Storage uses the hashed device-installation + canonical workspace + Local/Cloud namespace key, with a separate browser storage principal. **Phase 13 F04:** Cloud browser storage derives its stable owner from authenticated Cloud origin and account ID (or existing account email), while live sessions remain bound to the exact `instanceId` and token-specific `principalId`. This preserves consented profiles through token rotation without granting access to active browser session IDs across principals.

- Temporary: `~/.buildifyx/browser/v1/sessions/<browserOwnerKey>/bs_<uuid>/chromium`. Each session launches a dedicated Chromium user-data directory. Closing an idle/explicit/shutdown session removes **only** this generated, marked directory. Startup cleanup reclaims dead-process sessions after validating private metadata. Normal default idle expiry: **30 minutes**.
- Persistent: `~/.buildifyx/browser/v1/profiles/<browserOwnerKey>/profile_<sha256(name)>/chromium`. A persistent session requires both `confirmPersistent: true` **and** a positive `persistentConsent` callback. Calling `closeSession`, `closeAll`, cleaning temp sessions or clearing the image cache does **not** delete persistent profiles.
- Persistent Chromium profile state is kept locally. To make cookies reliable across Playwright/Chromium restarts, the engine writes a 0600 private `browser-state.json` snapshot on clean close and reloads it on next consented open. The state may contain **sensitive cookies**; it is never logged, returned to an MCP tool, or uploaded to Buildifyx Cloud. Snapshotting on abrupt process termination is not guaranteed. Full profile reset/delete must be explicitly requested and will be provided by later permissioned tooling.
- **Migration of an old token-keyed profile:** after explicit `confirmPersistent:true` and `persistentProfile` approval, the engine may atomically rename only the matching named profile belonging to the **currently authenticated device token** into the stable account-owned directory. Migration refuses old live/stale locks, symlinks/hardlinks, unsafe entries and existing stable destinations. It reserves both new and old profile locks to prevent concurrent Chromium use; never copies cookies to Cloud. Legacy profiles from a token already rotated away cannot be safely identified, guessed, claimed or deleted automatically. Missing account ID/email falls back to token-scoped ownership, so rotation can leave the prior profile inaccessible without manual authorized recovery. Changing credential identity from email-only to account ID can also create a different stable key; no automatic reassignment is attempted.
- Private directories use 0700 permissions and state files 0600 where supported. All external names become validated or hashed internal path components. Symlink/hardlink-protected metadata reads, workspace/principal fencing and conservative crash cleanup refuse unknown state; no arbitrary directory can be supplied as a browser profile path.

## Engine API (internal)

`createBrowserSessionEngine({workspaceRoot, namespace, instanceId, principalId, storagePrincipalId?, legacyStoragePrincipalId?, chromium?, homeDirectory?, persistentConsent?, idleMs?, maxSessions?, now?})` produces:

- `initialize()`: prepare private state and reclaim only orphaned temporary sessions.
- `open({scope:{instanceId,principalId},kind:'temporary'|'persistent',profileName?,confirmPersistent?})`: isolated, headless Chromium context. No persistent profile is opened without explicit consent.
- `withSession(sessionId, callback, {scope})`: short-lived authorized internal access to the Playwright context for later Phase 6/7 tools; not a public tool callback.
- `list({scope})`, `closeSession(id,{scope})`, `prune()`, `closeAll()` for metadata listing, safe teardown, idle cleanup and process shutdown.
- `validateBrowserUrl(url)`: helper permitting HTTP(S) including `localhost` and `127.0.0.1`, rejecting user-info credentials, dangerous schemes and obvious private/internal network targets. **It is a preliminary syntactic guard, not a complete redirect/DNS/private-network protection**. Phase 6/8 must validate navigation destinations and every request/redirect/popup.

Default max simultaneous live sessions: **3 per engine** (configurable up to 8), one Chromium context per session, launch timeout 30 seconds, default Chromium headless. Chromium contexts disable downloads, service workers and ignored HTTPS errors by default. Browser engine does **not** attach to the person's normal Chrome profile, import their cookies, open a user-specified filesystem profile directory or create Cloud-side data.

## Installation and operating-system checks

`playwright` is a package dependency; installing the npm package **does not automatically install its Chromium browser binary**. On machines missing the browser, an attempted session fails with `BROWSER_LAUNCH_FAILED` and a message to run:

```bash
bdxa browser install
```

No browser binary installation occurs silently at runtime. macOS browser execution is validated by a real localhost Chromium smoke test. Windows/Linux validation and install documentation belong to the final release phase. A malicious website, redirect, downloaded file, cross-origin frame or login form must be treated as untrusted: Phase 5 does not expose browser actions to MCP yet.

## Boundaries for Phase 6/8

- Phase 6 adds `browser_open`, `browser_navigate`, `browser_snapshot`, `browser_click`, `browser_fill`, `browser_tabs`, `browser_close` to services, permissions and the MCP registry. Each call must bind the current local MCP session or authenticated Cloud principal and active workspace/instance, not trust user-provided identity fields.
- Phase 8 adds explicit permission categories, approval UX, browser-origin/redirect/private-address controls, data redaction, sensitive action authorization, concurrency and timeouts. Never treat persistent-profile consent or a browser session ID as a grant to submit forms or perform destructive actions.
- No changes were made to Agent Protocol v2, Management Protocol v1, Local MCP tool list, or Cloud image relay protocol in Phase 5.
- No automatic Cloud persistence of cookies, credentials, browser state or screenshots. **Local Browser Profiles may still contain secrets on disk** and depend on protection by the OS user account.

## Test gates

`npm run check`, `npm test`, `git diff --check`, and `npm audit --omit=dev`. Smoke test skips on hosts without installed Chromium; a passing macOS smoke verifies page load and persistent-cookie restore. Windows/Linux must not be reported as tested unless actually executed.
