# Phase 15 — Global approval visibility and safe TUI interaction (2026-10-13)

**Agent only / in-progress v0.4.0.** This phase does not deploy Cloud, change device credentials, update permission storage, or grant browser privileges globally.

## Implementation

- New pending Agent approval requests take visual and keyboard priority over **every** TUI screen: Dashboard, Permissions, Roots, Commands, Diagnostics, Help and background-handoff confirmation. The old screen, cursor/selection, input text and background-confirmation state remain intact and resume once approvals are answered or removed.
- One full-width bounded Approval view shows **category, tool, concise description, (when space permits) location and impact, the available choices, current pending count and key help**. Previous half-width Dashboard-only approval rendering was removed. When terminal space is insufficient, the existing resize fallback remains **fail closed**, not an implicit approval.
- The initial choice on **every new approval ID** is **Deny**, not Allow once. Keyboard up/down allows deliberate selection, Enter confirms, Q/Escape denies. A new concurrent request cannot inherit a previously selected Allow; queue order is stable and cancelled/expired requests are removed by the existing queue. Input from other screens cannot run underneath an unresolved prompt.
- Browser sensitive-action and persistent-profile prompts expose **Allow once / Deny only**; never a remembered blanket browser permission. Existing explicit **remember root/command** choices remain limited to their legacy cases.
- Local and attached dashboards use the **same overlay**. Attached `approval.resolve` now **awaits the owning Agent's RPC acknowledgement**; disconnected, expired or cancelled requests do not falsely report success. A per-prompt in-flight guard avoids duplicate keypresses while confirmation is pending.
- Approval descriptions, tools, categories, locations and reasons are normalized to **single-line bounded terminal-safe text** (no CR/LF, ANSI/control sequences) to protect the compact layout.
- Incoming `permission.requested` and `permission.cancelled` events update the status message. Ctrl+C retains the preexisting stop vs attached-detach semantics. Ordinary permission presets and stored policy remain untouched.

## Tests

- Added `test/tui-approval.test.js`: default Deny and once-only browser choices, legacy remember scopes, terminal layout thresholds, FIFO/ID ownership, cancellation and stale approval denial, attached acknowledged resolve vs disconnected/expired control, overlay precedence for all screens, control-character sanitization.
- TUI and Policy regression runs remain grouped to stay within remote command limits. Full interactive terminal/real Cloud UI automation belongs to **Phase 17**.

## Boundaries

- This phase provides **in-process TUI and controlled RPC/queue test coverage**, not proof of actual device/Cloud/ChatGPT live approval prompts.
- Never claim OS-level Browser network containment. The original RL01/RL02/RL05 live Release gates are still marked **LIVE NOT TESTED** from Phase 13.
- Phase 16 cancellation/error diagnostics and Phase 17 end-to-end regression remain pending. **Release remains HOLD.**
