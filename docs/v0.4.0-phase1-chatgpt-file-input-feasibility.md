# v0.4.0 — ChatGPT Image-to-Agent, Phase 1 Feasibility

Date: 2026-10-14
Scope: **read-only ChatGPT/MCP research and existing implementation review**. This report is the only Phase 1 repository change; no Agent/Cloud runtime source changes or image uploads were made.

## Decision

- **Documented platform path: CONDITIONAL GO.** OpenAI Plugin reference documents a ChatGPT file-input tool convention: a tool descriptor with `_meta["openai/fileParams"] = ["file"]` and a top-level file input whose schema declares `download_url`, `file_id`, optional `mime_type`, optional `file_name`. `download_url` and `file_id` must be required *within the file object*; `mime_type` and `file_name` must be declared but not required. At runtime a file-bearing tool call can receive a ChatGPT-provided download URL and file ID. This is a supported file-reference handoff, **not** automatic inline image bytes in a model-visible screenshot.
- **Current Buildifyx ChatGPT → Agent direct attachment: NO-GO / NOT IMPLEMENTED.** The currently connected `mcp__bdxa__` tool inputs do not declare a file-object parameter. Read-only inspection of Cloud `backend/src/modules/mcp/server.ts` found upload-ticket tools but no `openai/fileParams`; `git grep` in both repositories found no file-param descriptor. No user-provided image was available in this turn for an actual host file-input test. No verified byte transfer from ChatGPT attachment or generated image has taken place.
- **Generated-image and existing-chat-attachment availability: UNVERIFIED.** The file-parameter mechanism is documented, but that alone does not establish automatic access to any images embedded/generated in a ChatGPT conversation. The optional `window.openai.selectFiles()` may let a ChatGPT widget select user-authorized items from the file library where supported; `window.openai.uploadFile()` is an additional widget upload path. The file library itself is optional. Require explicit selection and a real client test rather than claiming implicit access.
- **Supported fallback: IMPLEMENTED INTERFACES, LIVE E2E UNVERIFIED.** Cloud offers same-account `create_image_upload` → user browser POST upload → `send_uploaded_image_to_agent`; the Agent accepts `image-import-v1`, stores a 5-minute RAM-only artifact and only writes a file after explicit `save_cached_image({artifactId,destinationPath})`. Production account/end-to-end compatibility must be proven separately in Phase 5.

## Official evidence (retrieved 2026-10-14)

1. OpenAI Plugin Reference — File APIs and Define file inputs: https://developers.openai.com/plugins/reference#file-apis and https://developers.openai.com/plugins/reference#define-file-inputs ; see tool `_meta["openai/fileParams"]`, object schema, runtime `download_url` and `file_id`.
2. OpenAI Plugin UI guide: https://developers.openai.com/plugins/build/chatgpt-ui — optional `window.openai.uploadFile`, `selectFiles`, `getFileDownloadUrl` extension, feature detection.
3. Distinguish from OpenAI API file inputs: https://developers.openai.com/api/docs/guides/file-inputs describes Responses API file inputs, **not** evidence that the Buildifyx MCP connector receives ChatGPT chat attachments by default.

## Verified current connection / repository facts

- Connected `mcp__bdxa__create_image_upload` takes only an optional workspace selector; `send_uploaded_image_to_agent` takes `uploadId` and optional workspace selector. There is no `file` typed input in any image-ingress tool currently advertised to this conversation.
- Cloud `backend/src/modules/mcp/server.ts` registers five separate upload tools with `z.object({ ...routingFields })` or an `uploadId` extension and does not define a ChatGPT file-param intake tool. **Cloud belongs to another active plan; it was read only.**
- Agent `src/transport/media/protocol.js` advertises `image-import-v1` and 128 KiB raw chunks. `src/transport/media/inbound.js` validates exact instance, current authenticated WebSocket/generation, up to 4 MiB, canonical Base64, ordered chunks, MIME and SHA-256; `src/transport/cloud.js` requires Cloud opt-in. The Image Service and Cloud upload documentation describe temporary RAM cache, local import permissions and explicit separate save.
- Baseline `git status --short --branch` before report: clean `cloud...origin/cloud`.

## Minimal future input contract (Cloud-owned proposal; not implemented)

Register a dedicated, explicit user-initiated Cloud MCP tool such as `import_chat_image`, retaining exact selected-workspace routing and authenticated OAuth principal:

```json
{
  "name": "import_chat_image",
  "inputSchema": {
    "type": "object",
    "properties": {
      "file": {
        "type": "object",
        "properties": {
          "download_url": { "type": "string" },
          "file_id": { "type": "string" },
          "mime_type": { "type": "string" },
          "file_name": { "type": "string" }
        },
        "required": ["download_url", "file_id"],
        "additionalProperties": false
      },
      "targetId": { "type": "string" }
    },
    "required": ["file"]
  },
  "_meta": { "openai/fileParams": ["file"] }
}
```

The actual Cloud integration must prove that its chosen MCP SDK preserves the descriptor metadata, passes the ChatGPT Plugin Scan Tools checks, and receives an authorized real file object from the live ChatGPT client. The file-param tool should *only* import into temporary Agent RAM. Saving requires a **second, explicit** `save_cached_image` user request, not a side effect of receiving the bytes.

## Security & authorization gates before implementation

- The host/user must explicitly authorize the specific file and destination workspace; no scraping private chats, guessing inaccessible IDs, or automatic access to chat/generated images.
- Download a file only after validating that it is a genuine **host-provided file parameter**, not a user-controlled arbitrary URL. Protect against SSRF, hostname/DNS rebinding, redirects, private IPs, excessive redirects, expired URLs, credential leaks and untrusted host impersonation; never accept plain HTTP or a general-purpose URL fetch API.
- Bind the file import to the same OAuth user, current MCP-selected device/instance and active Agent WebSocket session, MCP access revision and live account quota; recheck these at start, per chunk and commit. Do not modify Cloud access rules without separate plan authorization.
- Stream bounded max 4 MiB; verify downloaded bytes independently of declared type/name; allow only PNG/JPEG/WebP with magic, decoder, SHA-256, timeouts, cancellations and replay protection; discard Cloud staging on failure.
- Agent import requires `imageRead=Allow` and `cacheManage=Allow` (Ask/Deny do not silently pass). Permanent save uses separately authorized `imageSave`, selected new file path, collision and symlink/traversal protections; **never** auto-save or overwrite.
- No undocumented file bridge, generic untrusted upload URL, production credentials, permissive fallback or image bytes in `run_command` / `write_file`.
