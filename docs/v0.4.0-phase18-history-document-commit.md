# Phase 18 — Fix History API forged Browser document commit (2026-10-13)

**Workspace:** `MCP-remote.Buildifyx`, version 0.4.0, uncommitted working tree on `cloud`. Phase 18 only; final Phase 12 read-only review has **not** been performed after this fix. No Commit/Push/Publish/Deploy.

## Finding from failed Phase 12 / Plan Revision 31

**HIGH:** The old-page `history.replaceState()` event was treated as proof that an explicitly requested new browser document committed. In `src/browser/network.js` the Playwright `framenavigated` handler checked only `frame.url()` against the expected URL after `route.fetch`; that event also fires for same-document History API changes. It could set `pending.documentCommitted` while the hostile old DOM was still executing, release the pending/safe-click network restrictions, and allow unintended old-document GET image beacons.

**Red proof (real Chromium):** Controlled local HTTP fixture intentionally held `route.fulfill` for 300ms while an old page repeatedly called `history.replaceState({}, '', '/target')` and issued `new Image().src='/unsafe?...'`. Initial `test/browser/phase18-pending-origin.test.js` run: **5/6 tests pass; new history race test fails with 77 unexpected GET requests** (expected zero). This is isolated, reproducible security evidence, not production traffic.

## Fix

- `src/browser/network.js`: Replace generic Playwright `framenavigated` URL matching with a per-tab **Chromium CDP `Page.frameNavigated`** watcher scoped to the actual **main frame ID and a changed document `loaderId`** established by `Page.getFrameTree` before granting navigation. `Page.navigatedWithinDocument` (history API / hash / same-document) is **not** a new-document commit. URL equality alone is never enough.
- Until the actual CDP main-document loader changes *and* the verified route-served document URL matches, `pending.documentCommitted` remains false, so prior-page resource GETs stay blocked even while `route.fulfill` is delayed. A document that has genuinely committed can load its own same-origin resources before Agent post-navigation confirmation, retaining required Chromium page bootstrap behavior.
- **Fail closed** when CDP session setup, `Page.enable` or `Page.getFrameTree` validation fails or is unsupported: throw `BROWSER_URL_DENIED` **before setting `origins`/pending grant**. CDP sessions are scoped per page and detached on close/guard shutdown. Pending/failed navigation still revokes the temporary grant.
- Add `test/browser/mock-cdp.js` (test-only) to give existing F01/R02/Phase18 error fixtures verified synthetic CDP main-frame loader changes. Unlike the previous mock `framenavigated`, `sameDocumentNavigation` cannot unlock pending old-page GETs. No permissive non-CDP fallback was introduced into production.
- This Phase does **not** change browser permission categories, Cloud auth, redirect-chain validation, the 8-step redirect limit, image/cache serialization, or the prior duplicate Cloud Request ID fix.

## Boundaries

- Browser network egress still relies on Playwright in-process routing/DNS checks. **There is no OS-enforced network confinement or DNS pinning**. A host/browser exploit is not contained by this module.
- CDP document-loader verification is Chromium-specific; browsers lacking CDP fail closed rather than weakening approval. Real native Windows, GitHub six-runner CI, production Cloud/ChatGPT ImageContent and actual signed-in device upgrades remain **LIVE NOT TESTED**, with previous mock and code-level validation documented in Phase 13/17 signoffs.
- Phase 12 **final read-only diff review remains pending**. This Phase fixes the confirmed defect; it does not authorize release. **Release remains HOLD**.
